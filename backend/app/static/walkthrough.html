IIoT Device Monitor

A real-time status app for industrial devices onboarded over OPC-UA or Modbus — an edge gateway reads them on-site, a cloud backend stores and evaluates the readings, and a live dashboard shows what's happening right now. This page walks through how it fits together and how to use it.

01

How a reading gets from a device to the dashboard

OPC-UA and Modbus devices normally sit on an isolated plant network, not reachable from the internet. The gateway is the only thing that talks to them directly — everything past it only ever receives what the gateway chooses to send.

02

Onboarding many devices without re-teaching the system

A Device Template captures a device type once — its protocol and full tag/register map. A Device Instance is one physical unit created from a template by supplying only its connection details. The gateway picks up new instances on its own, on a schedule.

Single device

Pick a template, fill in the connection details (host/port/unit ID, or an OPC-UA endpoint), run Test Connection for a live read before saving, then onboard.

Bulk CSV

One template, many rows — device_name, host_or_endpoint, port, unit_id_or_node_prefix. Every row is validated independently, so one bad IP doesn't block the rest of the batch.

Custom devices

No matching template yet? Define tags inline for a one-off device, and optionally save it as a template afterward for reuse.

03

The Live Dashboard

Four running totals up top, then one card per device. Cards carry a sparkline per tag built from a rolling in-browser history, a quality dot, and a health state that degrades to Stale on its own after 8 seconds without a reading — not just when a value looks wrong.

Reading a card

Protocol badge top-left (Modbus / OPC-UA), overall health top-right. Each row below is one tag: name, trend, current value.

Beyond the sparkline: real history

The sparkline only shows what's accumulated in the browser since the page loaded. Click any tag row and it opens a chart backed by GET /api/readings/history, which uses TimescaleDB's time_bucket() to downsample on the way out — 1-minute buckets for the last hour, up to 2-hour buckets for the last week — so a 7-day view stays a few hundred points instead of everything TimescaleDB has stored. Range buttons: 1h · 6h · 24h · 7d.

04

Thresholds, alerts, and notifications

A rule watches one tag on one device. It fires once on the transition into breach and clears once on the transition back — not once per reading — so a sustained breach doesn't flood the feed.

Example rule

device-modbus-pump-1 / temperature_c > 85, severity Critical. The moment a reading crosses 85°C, one AlertEvent is created, pushed live to every open dashboard, and handed to the notifier. It stays active — and visible — until a later reading drops back at or below 85°C.

[STUB EMAIL -> ops-team@example.com] [CRITICAL] device-modbus-pump-1 / temperature_c > 85.0 (current value: 91.4) [STUB SMS -> +15555550100] [CRITICAL] device-modbus-pump-1 / temperature_c > 85.0 (current value: 91.4)

Email and SMS delivery are stubbed — logged in this exact shape rather than sent — until a real provider is configured. Wiring up Twilio or SMTP/SendGrid later means filling in two functions in notifier.py; nothing else in the pipeline changes.

05

Getting started

  1. Bring the stack up
    From the project root: docker compose up --build. This starts the two device simulators, the MQTT broker, TimescaleDB, the backend, and the edge gateway.
  2. Open the dashboard
    http://localhost:8000 — seeded with a demo org, one gateway, and the two devices below, already streaming.
  3. Look at what's already onboarded
    The Devices tab lists every instance; View shows its full tag map and connection config.
  4. Onboard one more
    From the Device Templates tab, or straight from Devices → Onboard Device using a template already on file.
  5. Set a threshold
    In Alerts, pick a device and tag, choose a condition and threshold, and save — it takes effect on the next reading.

06

Built, and what's next

✓ Built & verified

  • Modbus + OPC-UA edge connectors, polled from a single gateway loop edge-gateway/gateway/connectors/
  • Local buffering + replay on broker disconnect
  • Device Template / Instance onboarding, single + bulk CSV, live Test Connection
  • Gateway hot-reload via config polling — no restart to onboard
  • Live dashboard: KPIs, sparklines, staleness detection, search/filter
  • Threshold alert rules, edge-triggered lifecycle, live event feed, acknowledge
  • Stubbed email/SMS notification path
  • MQTT encrypted end-to-end with TLS self-signed local CA, auto-generated on first run
  • Historical trend charts backed by TimescaleDB time_bucket() downsampling, 1h/6h/24h/7d

→ Not built yet

  • Authentication & authorization every endpoint is open - by far the biggest gap
  • Real email/SMS delivery needs a Twilio / SMTP account
  • OPC-UA native subscriptions (currently polled on the same loop as Modbus)
  • Modbus RTU / serial support
  • Multi-tenant auth & org management screens
  • Rate-of-change alert conditions (only static thresholds today)
